The `zephyr_coredump` component helps debug crashes on [nRF52](/components/nrf52/) devices without a
debug probe. When the firmware crashes, Zephyr saves the CPU registers and the stacks of all threads
to a 32 KB partition at the top of the application flash. After the restart the stored dump is printed
in the log as hex-encoded `#CD:` lines and then erased. The Zephyr coredump tools turn that log into
a GDB session with a full backtrace.

```yaml
# Example configuration entry
zephyr_coredump:
```

The component has no configuration variables.

## Flash Layout

The partition is placed directly below the bootloader: at `0xEC000` with the Adafruit bootloader
layouts and at `0xD8000` on the nRF52840 dongle. With MCUboot it sits at the end of the 1 MB flash.
The generic `bootloader: adafruit` setting does not describe where the bootloader lives, so the
component rejects it; select one of the `adafruit_nrf52_sd*` bootloaders instead.

> [!WARNING]
> With [OTA updates for nRF52](/components/ota/zephyr_mcumgr/) the image slots end below the coredump
> partition, so enabling or disabling this component moves them. A device that already runs mcumgr OTA
> must be flashed over USB once after the change. An OTA update alone leaves the installed MCUboot with
> the old slot layout, and later OTA updates would silently fail.

## Reading the Dump

The dump is printed once a log reader is present and is erased right after. With a UART logger that is
at boot, so keep the serial monitor attached while the device restarts. With USB logging the device waits
until the USB port is opened, so a dump from a crash that happened hours ago is still printed when you
connect. Until then it stays in flash, where only the next crash replaces it.

The log looks like this:

```log
[14:36:08.267][E][zephyr_coredump:052]: #CD:BEGIN#
[14:36:08.267][E][zephyr_coredump:039]: #CD:5a450100030005001a0000004102004400d0670020b4670020efbeadde00b0ad
[14:36:08.269][E][zephyr_coredump:039]: #CD:de00000000296201002862010000000001505500200000000000000000000000
...
[14:36:08.321][E][zephyr_coredump:087]: #CD:END#
```

Save the log to a file and use the scripts from the `scripts/coredump` directory of a Zephyr checkout
together with the `.elf` file from the build directory of your device:

```bash
# Convert the log into a binary coredump
python3 coredump_serial_log_parser.py device.log coredump.bin
# Serve it to GDB
python3 coredump_gdbserver.py firmware.elf coredump.bin
# In a second terminal
arm-zephyr-eabi-gdb firmware.elf
(gdb) target remote localhost:1234
(gdb) bt
```

The [Zephyr coredump documentation](https://docs.zephyrproject.org/latest/services/debugging/coredump.html)
describes the tools in more detail. The dump holds every thread's stack with nRF Connect SDK 2.9.2 and
later; older SDKs store the faulting thread only.
